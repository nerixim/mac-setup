# Issue実装の規律

Issueを実装に落とす前の前提検証、設計判断の洗い出し、打ち切りの基準。着手前に一度通す。

## 1. 前提を潰す（省略しない）

計画を書く前に、Issueが立っている土台がまだ有効かを確かめる。潰す前提は3種類。

**(a) もう実装済みではないか**
マージ済みPR（`gh pr list --state all --search "<キーワード>"`）とコードのgrepを正とする。Issueの日付が新しくても本文は当てにしない。本文とコメントの「残タスク」記述は状態の正ではない。

**(b) 根拠として引用されている数字・計測が、本当にその主張を支えているか**
「ベンチでXが+2.7ポイント」「実測でYが98%」と書いてあるなら、その計測の条件を実際に読む。**本番に存在しない入力（正解ラベル、座標、人手の前処理）を使って出た数字は、本番の改善を意味しない。**

**(c) 前提となる別の変更・デプロイが済んでいるか**
「#XXX の修正が入ってから」という条件があれば、マージだけでなく**本番反映**を確認する。マージ済み≠本番稼働。

## 2. 設計判断を洗い出す

実装に入る前に、**選択肢が2つ以上ある箇所**を列挙する。特に:

- 動く場所（実行環境）のメモリ・タイムアウト・バンドル制約に触れるか
- 既存の分岐や転送方式（大きい入力の逃がし方など）を迂回しないか
- リモート状態（本番設定・feature flag・マイグレーション）を変えるか
- 呼び出し側lint・grepテスト・呼び出しごとのフラグで症状を止める案が出たら、ヘルパー／型でその出力を出せなくできないか。出せるならヘルパーを直す

該当がなければ黙って進む。

## 3. 打ち切る条件

次のどれかに当たるなら、実装に入らずそこで止める。

- 受け入れ条件が無く、何をもって完了かをIssueから決められない
- 引用されている計測が主張を支えていない（1(b)）
- 前提の変更・デプロイが未了（1(c)）
- 選択肢が2つ以上ある設計判断が未決で、どちらを選ぶかで成果物が変わる
- 要求が既に実装済み、または別手段で満たされている（1(a)）

**推測で埋めて進めない。** 埋めた前提が外れたPRは、レビューの時間を使ったうえで却下される。

## 4. 打ち切りの伝え方

伝えるのは「なぜ止めたか」と「次に誰が何をすれば動くか」の2点。崩れた前提は実測（コマンドとその出力、ファイルパス、PR番号）で示す。推奨付きで出し、開いた質問にしない。

## 5. 作業計画の書式

打ち切らずに進む場合、実装前に計画を出す。ファイル一覧やCIコマンドの羅列は入れない。

```md
**作業計画**

1. [具体的なステップ]
2. [具体的なステップ]

**影響範囲**
- [触るファイル・コンポーネント]

**検証方法**
- [テスト・実挙動の確認手段]
```

前提検証で分かったことがあれば、計画の前に「## 前提検証」として実測値付きで置く。
